# Circuit catalog roadmap (`breadboard-circuits/`)

This specifies how the imported `breadboard-circuits/spec/` corpus — 212
buildable circuits across 20 sections, with finished schematics and a
machine-readable `catalog.json` validated by its separate
`catalog.schema.json` — turns into bredboard content. It is a
**specification**, not an active Goal: no task card here is ready to execute.
Each phase below still needs its own dedicated specification and
commit-sized task cards, the same way [LESSONS.md](LESSONS.md) decomposed
into T19–T27, before any of it is implemented.

The reference-only `breadboard-circuits/circuits-catalog.html` page keeps the
20 sections separate and provides client-side search; this does not make the
212 schematics runnable app fixtures.

## Constraint carried over from the source spec

`breadboard-circuits/spec/README.md` bans anything programmable (no
microcontrollers, no firmware, no bus-addressed EEPROM) and restricts power
to 5–12 V batteries/adapters — this already matches `AGENTS.md`'s "Rust core
must not depend on ... programmable devices" boundary, so the corpus needs
no scope negotiation on that point. Its own schematics are "generated by
schemdraw and checked by eye ... must be verified against the solver and a
real board before publishing a level" (`spec/README.md`); treat every
schematic as a reference to validate, not a ground truth to trust.

## Why this is bigger than E11–E30

[docs/roadmap/POST-MVP.md](POST-MVP.md) already says: after E30, pause
content expansion and specify data-driven level metadata, declarative
completion conditions, and a project-format migration path before targeting
a substantially larger catalog; add a local `.cir` exporter and ngspice
differential checks before relying on the numerical model for a larger
corpus. This 212-circuit catalog is that "substantially larger catalog." It
does not fit the fixed-exercise-per-menu-entry pattern used through E30:
several sections describe multi-board systems (digital clock, robot,
solar station) with a block diagram instead of one schematic, and section
20 is a different game mode (find-the-fault pairs), not a buildable circuit
at all.

## Phase 0 — prerequisites (must land before any phase below)

1. **Level metadata and migration path.** The exact deferred item from
   `POST-MVP.md`'s "Current direction" paragraph. 212 circuits need
   data-driven level definitions; hand-writing 212 more fixed-fixture JSON
   files the way E1–E30 were written does not scale and each new component
   family below would otherwise force a project-format break.
2. **`.cir` exporter and ngspice differential checks.** Also already
   required by `POST-MVP.md`. Needed to validate the source spec's
   schemdraw schematics (explicitly unverified against a solver) before any
   are turned into levels, and to catch solver-vs-reality gaps once
   component families in Phases E–I introduce non-ideal behavior (motor
   back-EMF, relay coils, AC rectification).
3. **Per-section scope decision.** Decide, once per section, whether its
   circuits become individual fixed exercises (like E1–E30), a free-assembly
   unlock set (`POST-MVP.md` phase 1), or are descoped. Sections 18 and parts
   of 08/13/19 include non-breadboard physical props (a lemon, a cup of
   water, a donor toy/printer/CD drive, a soldering iron) that cannot be
   represented as board holes at all; flag these explicitly rather than
   silently dropping them during implementation.

## Gap analysis: new component families needed

Extracted from every BOM in `spec/catalog.json` (282 distinct part names).
Grouped by what new engineering they require, independent of section. See
[the design expansion plan](../design/sprites/CATALOG-EXPANSION-PLAN.md) for
the matching sprite/UI gap list.

| Family | Representative parts | Rough BOM hits | New capability needed |
| --- | --- | --- | --- |
| Timer/comparator/op-amp ICs | NE555/NE556 (73), LM393 (14), LM358 (11), TL072/074 (16), LM386 (8), LM3914 (8), LM339 (1) | ~130 | Multi-pin IC package abstraction; op-amp and 555 educational models (`POST-MVP.md` phase 3 already names op-amps) |
| Digital logic ICs | 74HC00/08/32/86/74/14/393/595/283/138/154/... , CD4011/4013/4017/4060/4093/4511/... | ~120 | The separate digital-logic plan `POST-MVP.md` already flags: gates, flip-flops, counters, shift registers, event scheduling alongside analog time-stepping |
| Ready-made behavioral modules | PIR HC-SR501, IR receiver TSOP38238, HC-SR04, MQ-2, ISD1820, PT2262/2272 pair, 433 MHz TX/RX pair, ULN2003/2803, TP4056, KY-038 | ~30 | No current abstraction: a "black-box" component with a documented pin-level input/output contract and no internal simulation, distinct from a modeled electrical device |
| Electromechanical / motion | DC motor, TT gearmotor, SG90 servo, 28BYJ-48 stepper, solenoid, vibration motor, fan, pump, relay SPDT/DPDT | ~70 | A motor/relay/actuator solver domain: torque-current or coil-contact behavior, PWM position/speed, H-bridge (L293D) and Darlington (TIP120/ULN2003) driver models. | Displays/indicators | 7-segment (common cathode + anode), 10-LED bargraph, 8×8 LED matrix, RGB LED | ~30 | Multi-segment/multi-cell component rendering driven by several digital outputs at once |

| Discrete parts already speced but not implemented | Rectifier/signal diode, PNP transistor, ceramic capacitor, colored LEDs, slide/toggle switch | ~110 | Already designed in `docs/design/sprites/README.md` "Future parts"; each still needs its own electrical model and task card — no new design work |
| Instrumentation / biosignal | INA128/AD620 instrumentation amp, JFET 2N5457, ECG electrodes, skin-contact electrode, Hall sensors (SS49E analog, A3144 digital) | ~10 | Very-small-signal educational models; skin/body as a signal source is a novel, safety-reviewed abstraction (battery-only, already required by the source spec) |

Passive values (resistors, standard ceramic/electrolytic/film capacitors,
crystals) need no new component kind — only expanded catalog *value* ranges,
already the kind of change T15 made for capacitor/transistor ranges.

## What this document does not do

It does not create Codex Goals, task cards, or new `ComponentKind`s. Each
phase (A–M) needs the same treatment `LESSONS.md` gave E11–E30: a dedicated
specification naming exact component models, solver changes, and
commit-sized cards, requested and written one phase at a time. Do not start
implementing any phase from this document alone.
